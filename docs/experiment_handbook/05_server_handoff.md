# 服务器反馈与协作

## 1. 你现在可以做的准备

1. 阅读 [总览](00_overview.md) 和 [验证路线](01_validation_plan.md)，确认第一轮范围。
2. 执行 [环境盘点](02_environment.md) 的只读命令，填写 [服务器信息模板](../templates/server_inventory.md)。先反馈结果，再决定候选环境是否适用。
3. 若数据目录/网络已确定，下载 DanceTrack 的 `train1.zip`、`train2.zip`、`val.zip`，完成压缩包检查；记录实际路径和剩余空间。
4. 反馈已有检测权重、数据或缓存；来源不明的现成文件可以帮助排错，但需要查明版本后再进入正式对照。
5. 下一轮我们根据反馈实现 M0–M1。先得到一段视频的可靠基线闭环，再扩大到错误分析与模型训练。

现在不用同时配置 8 张卡的分布式训练，不用下载全部 MOT 数据集，也不用为每篇相关论文创建环境。

## 2. 首次反馈的最小内容

- Linux 发行版、CPU、内存、磁盘空余与可用目录。
- GPU 型号/数量/驱动；8 张 4090 是否同机、是否独占；3060 所在机器。
- Conda/Mamba/Docker/Slurm 等已有工具；是否允许安装用户级软件。
- GitHub、PyTorch wheel、Hugging Face 能否访问，是否需要组织规定的代理或镜像。
- 可用 GPU 时段、任务时长限制、数据保留/清理规则。
- 当前准备到哪一步、准确执行命令、错误原文。
- 毕业时间、学院对方法创新/系统/投稿的具体要求（如已知）。

可以先提供这些信息，不需要等待所有环境装好。网络、驱动、依赖或下载问题本身就是决定实现方案的依据。

## 3. 运行管理

普通服务器使用已有 tmux/screen，集群使用其作业调度器。日志写入各自 run_id；实验启动前记录 GPU 分配和输出路径。共享机器不自行终止别人的任务，也不批量更改驱动和系统软件。

每次反馈使用 [实验记录模板](../templates/experiment_record.md)：命令、提交、环境、阶段、关键指标、日志路径和错误。没有运行到评测阶段时写“未产生结果”，不要把训练 loss 当成 HOTA 的替代。

结果进入 Git 前只保留轻量摘要、配置、清单和必要图表；图片数据、权重、原始大日志和服务器私有信息保留在数据目录。`local/` 被忽略，适合保存填写后的服务器细节；不要把密码、token、私钥写入模板或仓库。

## 4. 以后让助手操作服务器时

你准备好后，再提供可用的连接方式或已配置的 SSH 别名、允许操作的项目目录、数据目录、GPU 配额和调度规则。凭据通过已有安全连接配置使用，不需要粘贴到聊天或提交 Git。

首次远程操作的顺序建议为：只读盘点 → 核对 Git 工作区和路径 → 小样本验收 → 短任务 → 有日志和预算的正式任务。当前这轮没有连接服务器，也没有安装软件、下载数据或启动训练。

已确认的授权与资源范围会作为后续执行依据，不重复请求相同操作的确认；超出资源范围、影响系统配置或其他任务的动作另行说明。

## 5. 何时进行路线复盘

G2 错误归因完成、G3 简单模型对照完成、G4 梯度对照完成各复盘一次。每次填写 [决策记录](../templates/decision_record.md)，明确“继续”“先排错”“调整研究问题”及依据。失败实验也保留，它们帮助缩小有价值的创新空间。
